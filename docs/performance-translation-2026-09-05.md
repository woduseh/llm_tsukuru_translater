# 병렬 번역 측정과 Gemini Flash latest 운영 기준

2026-09-05 기준. 실제 Gemini API 사용료를 발생시키지 않고, 생산 코드의 번역 coordinator → registry/factory → Gemini 요청 경로에서 `axios.post`만 모의 응답으로 교체해 측정했다.

## 일반 사용자 권장값

| 사용 조건 | 동시 API 요청 수 |
| --- | --- |
| 무료 계정 또는 실제 한도 미확인 | 1로 시작 |
| 결제가 연결된 일반 사용자 | 2로 시작 |
| AI Studio의 RPM·입력 TPM 여유를 확인한 사용자 | 4까지 늘려 확인 |
| 충분한 할당량과 실제 처리량·429·토큰 사용량을 측정한 사용자 | 8을 선택할 수 있음 |

이는 Google의 공식 동시 요청 제한이 아니라 이 앱의 시작 기준이다. 앱 기본값은 1을 유지하고, 구현 상한은 8로 둔다. 설정 이름을 **동시 API 요청 수**로 바꿨으며, 파일과 청크의 요청을 모두 합산한다. 파일 단위 번역은 여러 파일이, 청크 단위 번역은 한 파일 안에서도 병렬 실행된다.

[Google 공식 Rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)는 현재 활성 RPM·입력 TPM·RPD를 프로젝트의 AI Studio에서 확인하도록 안내한다. 모델·tier·계정에 따라 값이 달라지므로 과거 무료/유료 RPM 수치를 공통 상한으로 고정하지 않았다. 한도는 프로젝트 단위여서 같은 프로젝트를 쓰는 다른 API 키나 앱도 영향을 준다. 문서의 Batch 동시 100개는 여기서 사용하는 일반 generateContent 요청에 적용하는 수치가 아니다.

새 **분당 API 요청 수(RPM)** 설정은 `0`이면 앱의 별도 속도 제한을 끈다. 기본값도 0이며 동시성 제한과 429 대기는 계속 적용된다. 실제 RPM 한도의 약 80%를 시작값으로 입력하고 TPM도 확인하도록 UI에 안내한다. 80%는 재시도와 변동을 위한 앱 권장 여유이며, 다른 앱의 사용량이 크면 여유를 더 남겨야 한다. 동시 요청이 1개여도 응답이 빠르면 RPM을 넘을 수 있다.

평균 요청 완료 시간 `L`초, 시스템 프롬프트를 포함한 평균 입력 `P`토큰, 동시 요청 `C`개일 때의 대략적인 지속 부하는 다음과 같다. 서버 지연이 달라지면 실제값도 바뀌며, 입력 TPM 외에 RPD 등 다른 한도도 별도로 충족해야 한다.

```text
예상 RPM       = 60 × C / L
예상 입력 TPM  = 60 × C × P / L
```

`gemini-flash-latest`는 [자동으로 대체되는 모델 alias](https://ai.google.dev/gemini-api/docs/models#latest)다. 공식 모델 목록에는 최신 stable `gemini-3.8-flash`가 있지만, 이번 조사로 alias의 실제 응답 모델을 확정하지는 않았다. 실제 계정의 응답 `modelVersion`과 해당 모델 할당량을 확인해야 한다. 저장된 모델을 자동 변경하지 않고 alias와 3.8을 추천 목록에 추가했다.

## 병목과 구현

변경 전에는 Gemini/Vertex의 파일 작업을 강제로 1개로 제한했고, 파일 내부 청크도 순차 실행하며 청크 사이에 1초를 기다렸다. 짧은 요청이 반복되는 입력에서는 이 고정 대기가 모델 응답보다 큰 비중을 차지했다. 파일 작업 수만 늘리면 단일 대형 파일은 그대로 느리고, 파일/청크에 각각 제한을 두면 실제 요청 수가 곱해질 수 있다.

- `src/ts/libs/translationRequestScheduler.ts`: 번역 실행마다 하나의 scheduler를 공유한다. 최대 8개의 요청, FIFO 대기, 선택적 RPM 시작 간격, 공유 429 대기, 취소 가능한 대기를 제공한다. 대기 작업을 한꺼번에 전체 청크 수만큼 생성하지 않고 파일/청크 worker 수로 제한한다. coordinator의 동시 청크 작업은 최대 `C²`개이며 실제 provider 요청은 최대 `C`개다.
- `src/ts/libs/providerTranslationBase.ts`: 기존 청크 경계와 한글 건너뛰기를 유지한 채 병렬 실행하고 원래 인덱스로 재조립한다. 실패한 청크만 재시도한다. API 재시도 횟수를 소진하면 검증 재시도 예산으로 추가 API 재시도를 하지 않는다.
- `src/ts/libs/providerRetry.ts`, `translationCore.ts`, `geminiTranslator.ts`: 비밀정보가 포함된 원본 Axios 객체를 보존하지 않고 status와 재시도 지연 숫자만 전달한다. Retry-After의 초/HTTP 날짜와 Google RetryInfo의 서버 대기 중 가장 긴 값을 지킨다. 서버 힌트가 없으면 제한된 지수 backoff와 jitter를 사용한다. 429 대기는 요청 permit을 반환하기 전에 공유한다.
- `src/ts/rpgmv/translator.ts`: 파일과 청크가 같은 제한을 사용하고 전체 진행률을 합산한다. 파일 검증·원본 변경 확인·원자적 저장·캐시·재개 진행 상태를 유지한다. 취소 및 callback 실패 시 진행 중 요청을 모두 기다린 후 반환한다. 실행 전체를 중단시킨 내부 오류는 정상 완료로 보고하지 않는다.
- `src/renderer/views/LlmSettingsPage.vue`와 설정/IPC: 동시 요청 수 1/2/3/4/8 선택, RPM 입력, 권장값과 잘못된 입력 안내를 연결했다. 저장된 5~7도 표시해 보존한다.

최신 모델 호환성으로 latest alias와 명시적 3.8의 마지막 model prefill을 제거했다. [공식 generateContent migration checklist](https://ai.google.dev/gemini-api/docs/generate-content/latest-model#migration-checklist)가 마지막 user turn과 prefill 제거를 요구한다. 시스템 프롬프트와 번역 원문은 동일하며 과거 고정 모델의 prefill은 유지한다. 따라서 변경 전후 전체 HTTP body는 의도적으로 같지 않고, 벤치마크에서 이 차이를 별도로 기록한다.

## 측정 조건과 결과

- Windows `10.0.26200`, x64, Node `v24.14.0`, AMD Ryzen 7 7800X3D, 논리 CPU 16개.
- 동일한 8개 청크를 ① 한 파일의 8개 청크, ② 파일 4개에 청크 2개씩 배치했다. 구분자, 빈 줄, 일본어, 제어 코드를 포함한다.
- 청크 크기 1, 모델 설정 `gemini-flash-latest`, API/검증 재시도 0, RPM 제한 0. 모의 응답 시간은 `120 + (chunkId % 3) × 40`ms이며 순서가 뒤바뀌도록 구성했다.
- 모든 변형에서 동일한 원문·시스템/사용자 프롬프트·성공 요청 8회·기대 번역 바이트를 검증했다. 캐시, 진행 파일, 원본 백업과 원자 쓰기도 확인했다.
- 변형/시나리오마다 워밍업 1회 후 3회 측정했다. 실행 순서를 회차마다 정방향/역방향으로 바꿨고 모든 측정은 순차 실행했다. 매번 새 파일과 빈 번역 캐시를 쓰되 OS 파일 캐시는 비우지 않았다.
- 시간에는 coordinator, provider 처리, 구조 검증, 번역·캐시·진행 파일 쓰기와 fsync를 포함한다. 모듈 빌드/로딩, fixture·백업 준비, 사후 비교 검증, 정리는 제외한다.

고정 대기를 없앤 변경 후 동시 1개와 비교하면, **동시 4개는 각각 3.30배 / 3.40배 빠르다.** 변경 전과 직접 비교한 큰 개선 폭에는 1초 대기 제거도 포함되므로 이를 전부 병렬화 효과로 해석하면 안 된다. 실제 최대 요청 수는 모든 변형에서 정확히 설정값 1/2/4/8이었고, 성공 요청 수는 모두 8회였다.

CPU 시간도 원시 결과에 기록했지만 짧은 실행에서 Windows 측정값이 0/15/16/31ms처럼 나타나므로 CPU 비용 개선 근거로 사용하지 않는다. 실제 Gemini의 응답 시간, 처리량, 번역 품질이나 토큰 요금 절감 수치로 확대 해석하지 않는다.

기준 소스는 실행 경로 변경 전에 `.source` 확장자로 보관했다. 먼저 실행한 `before.json`의 중앙값은 8440.0ms / 5458.7ms다. 위 표는 변경 후 같은 프로세스에서 기준 스냅샷을 다시 불러 순서를 교대한 `before-after.json` 결과다.

## 검증과 재현

이번 변경 전 기준 상태는 전체 단위 테스트 718개와 저장소 검증 `passed`, `sourceChanged=false`였다. 새 회귀 사례는 다음 동작을 검증한다.

- 단일/다중 파일의 요청 상한, 순서가 뒤바뀐 완료, 검증 인덱스와 진행률 증가.
- 한글 건너뛰기, 줄 수·빈 줄·구분자·제어 코드, 일부 청크 실패 시 원본 전체 파일/캐시/완료 상태 보호.
- RPM 시작 간격, 파일 간 429 공유 대기, 실패 청크만 재시도, 재시도 횟수와 비밀정보 제거.
- 대기 중 취소, 진행 중 요청 drain, 취소 직전 완료 파일 보존, 단발 callback 실패와 commit 실패 전파.
- 설정 직렬화, IPC 저장, Vue DOM의 잘못된 입력 차단과 수정 후 복구.

기존 테스트에서 취소 직전 완료 결과까지 버리는 회귀를 발견해 완료 여부(`result.aborted`) 기준으로 고쳤다. 독립 검토에서 callback 실패가 실행 전체를 멈췄는데 정상 완료로 반환하는 문제도 발견해 drain 후 오류를 전달하도록 수정하고 회귀 테스트를 추가했다.

```powershell
node scripts/benchmark-translation.cjs --before-only --runs 3 --warmups 1 --output artifacts/performance/translation-2026-09-05/recheck-before.json
node scripts/benchmark-translation.cjs --runs 3 --warmups 1 --baseline-dir artifacts/performance/translation-2026-09-05/baseline --output artifacts/performance/translation-2026-09-05/recheck.json
npm run verify:plan
npm run verify
```

원시 반복값·환경·소스 해시·요청별 시각·출력/프롬프트 해시는 `artifacts/performance/translation-2026-09-05/before-after.json`에 있다. 기준 소스 해시와 이전 검증 위치는 같은 폴더의 `baseline-state.json`에 있다. 최종 저장소 검증의 집계 상태와 check별 명령·로그는 `artifacts/verify/latest.json`에서 확인할 수 있다.

## 남은 한계

실제 Gemini 호출과 유료 서비스 사용은 하지 않았다. 따라서 계정별 최적 동시성, 실제 번역 품질, 토큰 사용량은 미측정이다. API 성공 경로의 청크 수는 늘지 않지만, 할당량 초과와 재시도가 생기면 실제 처리 시간과 비용이 달라질 수 있다.

RPM과 공유 대기는 한 번의 번역 실행에 적용된다. 다른 프로젝트의 별도 작업, 다른 앱/기기와 quota를 자동 공유하지 않으며 TPM·RPD를 자동 계측하거나 제한하지 않는다. 서버가 알려준 대기는 존중하되 일일 한도 소진을 해결해 주지는 않는다. 취소는 새 요청/재시도를 막고 전송된 요청이 응답 또는 timeout으로 끝날 때까지 기다린다.

자동 quota 조회/TPM 추정과 동적 동시성 조절은 이번 구현에 넣지 않았다. 모델 alias와 계정에 따라 달라지는 값을 추정해 제한하는 대신 실제 계정의 한도를 확인한 수동 RPM과 제한된 재시도를 제공한다. 기존 게임 파일 적용 경로와 앞서 완료한 Wolf 성능 개선은 유지했다.
